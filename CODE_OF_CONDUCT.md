# Code of Conduct

## What we're aiming for

A project where technical disagreement is welcome, people aren't, and contributors get clear, fair treatment regardless of who they are or how long they've been around.

## Expected behavior

- **Engage on the technical merits.** Disagree with ideas, code, and decisions — not with the people behind them.
- **Assume good faith.** Most rough edges in online communication are misreadings, not malice. Ask before escalating.
- **Be specific.** "This doesn't work" is less useful than "this fails on input X with error Y." Specificity respects everyone's time.
- **Accept feedback, give feedback.** Reviewers and reviewees both. A "no" with a reason is more valuable than a yes without one.
- **Credit others' work.** Cite the issue you're building on, the person who helped you debug, the prior PR your fix is based on.
- **Help newcomers.** Everyone was confused by gcloud at some point.

## Unacceptable behavior

The following will result in moderation action — warning, comment removal, issue/PR closure, or blocking, depending on severity:

- Personal attacks, insults, or slurs targeting any individual or group
- Harassment of any kind, public or private, including unwanted sexual attention, deliberate misgendering, or sustained disruption of discussions
- Discrimination based on race, ethnicity, nationality, religion, sex, gender identity, sexual orientation, disability, age, body, or socioeconomic status
- Threats of violence or wishing harm on others
- Publishing private information about anyone without their consent ("doxxing")
- Sustained off-topic disruption, brigading, or bad-faith argumentation designed to wear others down
- Sexualized language or imagery in any project space
- Other conduct that would reasonably be considered inappropriate in a professional setting

Disagreement is fine. Frustration is fine. Treating other contributors as obstacles, opponents, or targets is not.

## Where this applies

This Code of Conduct applies in all project spaces:

- The GitHub repository (issues, pull requests, discussions, code reviews, commit messages, wikis)
- Any communication channels associated with the project
- When representing the project publicly — for example, in talks, blog posts, social media, or at events

It also applies when someone's conduct outside the project directly affects the safety or wellbeing of contributors inside it.

## Reporting

If you experience or witness behavior that violates this Code of Conduct, report it privately. **Do not file public issues for Code of Conduct concerns** — the goal is to handle them with discretion.

Channels:

- **Email the maintainer** at the address linked on the GitHub profile.
- **GitHub private security advisory** if you'd prefer a structured private channel (the same one used for security reports works for CoC issues too).

What to include:

- What happened, where, and when
- Who was involved (links to comments, PRs, or issues if applicable)
- Any context that helps assess severity
- What outcome you're hoping for (a warning, removal of a comment, a block, etc.)

You can report anonymously, but a reachable contact helps if clarification is needed.

## How reports are handled

The maintainer commits to:

- Acknowledging the report within a week
- Treating the report as confidential — details aren't shared beyond what's necessary to act on it
- Taking the report seriously regardless of who's being reported, including if it's the maintainer themself
- Communicating the outcome to the reporter

Actions may include, in roughly increasing severity:

- A private conversation with the person whose behavior was reported
- A public correction
- Removal of comments, commits, or contributions
- A temporary block from the repository
- A permanent ban
- Reporting to GitHub Trust & Safety if the behavior violates GitHub's [Acceptable Use Policies](https://docs.github.com/en/site-policy/acceptable-use-policies/github-acceptable-use-policies)

Severity is judged on impact, not intent.

## Honesty about the limits of a solo-maintained project

This project is maintained by one person in their spare time. That has implications:

- Response times to CoC reports are best-effort, not guaranteed
- There is no separate "moderation team" — the maintainer is judge and jury, which has obvious limitations
- If you have a CoC concern about the maintainer's own behavior, you can escalate to GitHub Support, who can take action independently
- The maintainer will recuse themselves from handling reports about people they have an obvious conflict of interest with, where practical

This isn't ideal — a larger project would have a moderation team and an appeals process. The honest acknowledgement is the best substitute available.
